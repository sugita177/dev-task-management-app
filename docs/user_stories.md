# DevTaskManagementApp: ロール別ユーザーストーリー＆ユースケース

本ドキュメントは、システムを利用する各役割（ロール）ごとの課題、実現したいシナリオ（ユーザーストーリー）、および受け入れ基準（Acceptance Criteria）を定義します。技術的な実現手法については[Phase 2 基本設計書](file:///c:/Users/81904/work_space/dev-task-management-app/docs/design_spec_phase2.md)を参照してください。

---

## 1. ENGINEER (開発エンジニア)
日々の実作業を担当。入力の手間を省き、作業への集中を第一とします。

### 🆔 US-ENG-01: マイ・フォーカスモードでの実績入力
* **ストーリー**: 開発エンジニアとして、全体ガントチャートなどの複雑な画面を開かずに、今日着手すべき自分のタスクだけを1画面で確認し、ワンクリックで実績時間を記録したい。
* **目的**: 迷いなく今日の作業に集中し、工数入力の漏れや手間を排除するため。
* **受け入れ基準 (Acceptance Criteria)**:
  - [ ] 専用のダッシュボードに「自分」がアサインされている「未完了」のタスクのみが表示される。
  - [ ] タスクカード上の「開始/停止」ボタンで、自動的に実稼働時間が計算され記録される。
* **関連技術仕様**:
  - API: `GET /api/tasks`, `POST /api/tasks/:id/work-logs`
  - DB: `work_logs`

### 🆔 US-ENG-02: マイ・ガントチャートとセルフキャパシティ分析
* **ストーリー**: 開発エンジニアとして、自分専用のガントチャートを表示し、自身の見積もり癖（安全バッファ）を加味した無理のないスケジュールか自己点検したい。
* **目的**: プロジェクト終盤での炎上や過負荷を防ぎ、EMへ早めにSOSを出せるようにするため。
* **受け入れ基準**:
  - [ ] ワンクリックで自分の担当タスクのみに絞り込まれたガントチャートが表示される。
  - [ ] 過去の実績/見積もり比率から算出されたバッファ期間がうっすらと可視化される。
* **関連技術仕様**:
  - UI: ガントチャートフィルター
  - DB: `users.max_capacity_hours`, `work_logs`

## 2. ENGINEERING_MANAGER (EM / PM)
チームのマネジメント、アサイン状況の最適化、スケジュールの進行管理を行います。

### 🆔 US-EM-01: ドラッグ＆ドロップによるガントチャート操作
* **ストーリー**: エンジニアリングマネージャーとして、ガントチャート上のタスクバーをドラッグ＆ドロップして直感的にリスケジュールしたい。
* **目的**: タスクの予定変更を迅速に行い、スケジュール調整のストレスを減らすため。
* **受け入れ基準**:
  - [ ] バーの端をドラッグで期間変更、全体ドラッグで日付の平行移動ができる。
  - [ ] タスクの依存関係（クリティカルパス）が線で結ばれ、遅延影響範囲が赤く強調表示される。
* **関連技術仕様**:
  - DB: `task_dependencies` テーブル

### 🆔 US-EM-02: 期間別の精緻なキャパシティ（アサイン負荷）分析
* **ストーリー**: EMとして、「今週」「今月」など特定の期間に絞って、各メンバーの正確なアサイン工数と過負荷状況を確認したい。
* **目的**: タスクの期間が重なる「魔の火曜日」のような局所的な過負荷を見つけ出し、バーンアウトを防ぐため。
* **受け入れ基準**:
  - [ ] UIで「今週」「今月」などの期間フィルターを選択できる。
  - [ ] 選択期間とタスクの予定期間が重なる日数分だけ按分された工数が計算される。
  - [ ] 1日の稼働時間が 8h（または個人上限）を超過している日が赤く警告される。
* **関連技術仕様**:
  - API: 期間集計バックエンドロジックの追加

### 🆔 US-EM-03: 見積もりと実績の乖離（偏差）アラート
* **ストーリー**: EMとして、事前の見積もり工数に対して実績工数が大きく超過（例: 120%超）したタスクを一目で把握したい。
* **目的**: 計画とのズレを早期に検知し、原因分析（仕様変更か負債か）を行うため。
* **受け入れ基準**:
  - [ ] 実績工数が予定見積もりの120%を超えた時点でタスクカードに警告UIが表示される。

## 3. BUSINESS (ビジネスサイド / PO)
プロジェクトのマクロな進捗状況とリリース時期に関心があります。

### 🆔 US-BUS-01: ロードマップ・ビジネス進捗ビュー
* **ストーリー**: プロダクトオーナーとして、開発の技術的なサブタスク等を非表示にし、リリース単位・機能単位のマクロな進捗だけを直感的に確認したい。
* **目的**: ビジネス側の意思決定（マーケティングや顧客へのリリース告知）を適切なタイミングで行うため。
* **受け入れ基準**:
  - [ ] 「ビジネスビュー」に切り替えると、技術的詳細が隠蔽されたエピック/プロジェクト単位での進行度（%）とリリース予測日が表示される。
  - [ ] リリース予測日が期日を超過している場合は黄色で表示される。

## 4. ADMINISTRATOR (システム管理者)
セキュリティと組織統制を担います。

### 🆔 US-ADM-01: テナント・組織マスタの統制とセキュリティ
* **ストーリー**: システム管理者として、全APIアクセスがセキュアに保護されており、ユーザーの「組織（チーム）」が正しく分離・表示されることを担保したい。
* **目的**: 他テナントのデータ漏洩を防ぎ、エンタープライズ基準のセキュリティを満たすため。
* **受け入れ基準**:
  - [ ] すべてのリクエストにおいて JwtAuthGuard が通過し、短寿命の Access Token（15分）と Refresh Token で認証・認可される。
  - [ ] 画面ヘッダーにログインユーザーの正しい `organizationName` が表示される。
* **関連技術仕様**:
  - API: 全体JWT保護、`POST /api/auth/refresh`
  - DB: `organizations`, `refresh_tokens`
